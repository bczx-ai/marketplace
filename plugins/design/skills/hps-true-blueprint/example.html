// 图 01 · 受威胁的不变量

例外方案会打破的四条规则

今天所有面向守护进程的能力都遵守四条不变量。一扇直连后门会同时打破全部四条，而不只是某个团队所要求的那一条。

  • sidecar 是唯一进出的代理 — agent 代码不得直连守护进程套接字
  • 所有守护进程数据路径都源自同一个解析后的 RUNTIME_DATA_DIR
  • sidecar 进程标记只包含五个字段 — app、mode、namespace、ipc、source
  • 应用的业务逻辑绝不直接导入另一个应用的私有内部实现
已提出的例外3 个插件团队 — 过去两个冲刺内
声称的延迟~40ms/call — 从未被独立测量
获批后的审计覆盖0% — 直连调用绕过 sidecar 日志
回滚成本~3 weeks — 每个团队都要重写完整 IPC 路径
双栏版式：左侧是不变量清单，右侧是虚线规格表，量化所请求例外的代价——读起来像真实图纸上的材料表。

// 图 03 · 建议，分四个阶段推广

一个冲刺内把规则落地

冻结

本次评审后不再合入新的守护进程直连例外。现有三个继续观察。

迁移

在本冲刺内把三个例外请求全部改走 sidecar 代理。

强制

CI 关卡会让任何在 sidecar 边界之外导入守护进程内部实现的 PR 失败。

度量

审计覆盖看板按周跟踪一个季度；在下次评审时回报。

流程步骤带方括号 [01]–[04] 计数，像图纸上的详图标注。这就是建议：冻结、迁移、用 CI 强制、再完整度量一个季度。

// 图 03 · 修订单差异

直连对比仅走 sidecar IPC

方案 A — 批准例外

直连守护进程

  • 绕过 sidecar 的唯一审计轨迹
  • 三个独立套接字，三个独立影响范围
  • 若回退，每个团队约需 3 周拆解

方案 B — 本建议

仅走 sidecar IPC

  • 一个代理、一条审计轨迹，每次调用都有记录
  • +2ms 实测代价，没有团队撞到真正的天花板
  • CI 关卡让规则今后自我执行
对比：三个团队要求的例外对比现行规则。语义化的好/坏标记保持在锁定调色板内 — 珊瑚色与薄荷色读作红线批注。
