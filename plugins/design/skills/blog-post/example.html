为什么我们用 Rust 重写了同步引擎

Mira Hassan · 2026年4月22日 · 8 分钟阅读

两年来，我们的 Go 同步引擎一直够用。直到视频剪辑师开始出现在客户名单上，那些我们一直礼貌忽略的 GC 停顿，变成了无法再忽略的 bug 报告。

这个决定并不突然。我们盯着 GC 停顿分布的变化看了六个月，才承认数据想告诉我们什么。P50 延迟很棒，P99 则是一部恐怖片。真正写信来反馈的，是在活跃剪辑会话中同步 30 GB .psd 文件的客户。

重写整个同步引擎，听起来正是那种初创公司被告知永远不要做的项目。我们还是做了。下面是过程、让我们意外的地方，以及我会做得不一样的部分。

导火索：修不掉的 GC 停顿

Go 的垃圾回收器非常出色，但它本质上是一种取舍。我们的热路径在每次块差异计算时都分配短生命周期的缓冲切片——在我们的规模下，一个重度上传的用户会让回收器跑得足够频繁，P99 停顿悄悄越过了 50ms。

我们试过常规手段：用 sync.Pool 复用缓冲、调优 GOGC、减少合并路径上的分配。每一项都有一点帮助，但都没能把我们压到 20ms 以下，而我们真正在意的客户需要 5ms 以内。

「我们在 Go 里修不好这个问题。换一个没有 GC 的东西就能修好。」

我们的资深工程师 Sasha 在十月的一次会上这么说。他是对的。问题不是要不要离开 Go，而是换到哪儿，以及能保留多少。

留下了什么；丢掉了什么

CLI 留在 Go，控制平面留在 Go。在客户笔记本上热循环里做块级差异计算的那部分——换成了 Rust。边界收敛成一层 FFI 接口，带一套小而明确的协议。

上面这些数字是真实的，来自生产环境。但脱离上下文同样会误导：Rust 移植不只是去掉 GC，它同时去掉了一层我们从 Go MVP 时代就背着的抽象。

我会做得不一样的地方

一件事：FFI 边界。我们为了对称选了 cgo——当你到处都是 Go 的时候，用 Go 调 Rust 感觉是对的。但绑定仪式很脆弱，在写出一层统一处理它们的包装之前，我们因为字符串生命周期错误吃了两次生产事故。

如果今天重新开始，我会用 uniffi，或者从 schema 生成绑定。教训不是别用 cgo，而是跨越语言族的那一刻，就把边界当成外部 API 对待。
