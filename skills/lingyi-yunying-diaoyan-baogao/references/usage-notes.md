## 待收集字段

| 字段 | 必填 | 示例 / 说明 |
|------|------|-------------|
| 品牌名 | 是 | `<品牌名>`（含规格更好，如 `<品牌名> <规格>`） |
| 卖点 | 否 | `<产品卖点/差异化点>` |
| 项目/公司背景、目标人群 | 否 | 合并写进 background_context |
| 调研目的(用户原话) | 否（采集后还会细化） | `<想搞清楚什么，如行业怎么卖/竞品怎么打/某卖点怎么合规表达>` |
| 渠道采集 | 是 | 至少一个平台（抖音/视频号）含对标账号或关键词 |

## 采集配置规范

- 平台 key 仅 `douyin`、`wx_video` 实采；`xhs` 传了会被忽略，引导用户别填。
- **必须用嵌套形态** `--platforms-json`（对象，每平台独立配账号/词/limit）。扁平的顶层 `accounts`/`keywords` 数组会被服务端 422 拒（已实测）。
- 每个平台 `accounts`（对标账号 ID/标识）与 `keywords`（关键词）至少给其一。
- `accounts_content_limit` / `keywords_content_limit` 默认 5、范围 1–20；越高越耗点数越慢——主动提示权衡。
- 各平台账号总数 ≤200、关键词总数 ≤200。
- 关键词尽量分平台差异化配（同一通用短词不必两平台都抓，避免噪音与重复扣点）。
- 未采集的平台在采集配置里**省略**，不要传空。

`--platforms-json` 示例（嵌套形态，分平台差异化配额；以下为占位，按实际替换）：

```json
{
  "douyin": {
    "accounts": ["<对标账号1>"],
    "keywords": ["<关键词1>", "<关键词2>"],
    "keywords_content_limit": 5,
    "accounts_content_limit": 5
  },
  "wx_video": {
    "keywords": ["<关键词3>", "<关键词4>"]
  }
}
```

## 入参 JSON 结构（写盘留档）

把收集到的入参写成 `social-research-input.json` 留档（采集源从中组装 `--platforms-json`）：

```json
{
  "brand": "<品牌名>",
  "selling_points": "<卖点（选填）>",
  "background_context": "<背景/目标人群（选填）>",
  "user_prompt": "<用户的调研目的原话（采集后细化）>",
  "capture_summary": {
    "sources": [
      {"platform": "douyin", "source_ref": "<关键词>", "source_type": "KEYWORD", "content_limit": 5},
      {"platform": "douyin", "source_ref": "<对标账号>", "source_type": "ACCOUNT", "content_limit": 5}
    ],
    "platforms": ["douyin", "wx_video"]
  }
}
```

- `sources[]` 的 `platform`/`source_type`/`source_ref`/`content_limit` 用于你组装 `--platforms-json`；
  `sources` 本身不直接传给服务端。
- 含时间戳可备份。

## 收集流程

1. 触发 skill 后先判断**采集硬门槛**是否齐全：① 至少一个平台（抖音/视频号）；② 该平台至少给账号或关键词。品牌名也必填。
2. **必填齐全** → 直接进阶段1（扣点确认后采集）。
3. **采集源缺失**（平台没给 / 给了但账号+关键词都空）→ 追问 1 轮，明确告知"平台和采集源是必填项、缺了无法发起"。话术示例：
   > 帮你做社媒运营调研报告（采集抖音/视频号素材 → 对齐分析方向 → 服务端生成报告）。
   > 还缺采集源，没它我没法开跑——
   > 1. **品牌名**是？
   > 2. **采哪个平台**？抖音 / 视频号（至少一个）；
   > 3. **对标账号 或 搜索关键词**，至少给一个：想看某账号内容→给账号名；想看热门词相关→给关键词。
   > 卖点、背景、目标人群、调研目的有就给，没有我也能采，但给了报告更贴你的业务。
4. **仍不给** → 采集源/品牌名缺则**终止并说明缺什么**（硬门槛不允许跳过，绝不发空源请求、不扣点）；
   选填项缺则用空继续不阻塞。

要点：一次问清，不挤牙膏；不向用户展示技术字段名（brand/platforms/deferred 等不出现）。
**采集源是硬门槛**：服务端对"嵌套 platforms 但 accounts+keywords 都空"会返 `400 At least one account or
keyword is required`，但对"请求体形态不对"只返 `422 Request validation failed`（detail 为空、不可读）——
所以**不能依赖服务端兜底**，必须在 skill 侧拦死。

## 字段完整性校验清单

### 门① · 采集前（调 create 前）

满足全部才发请求（前 3 条是**采集硬门槛**，缺一不可）：

- [ ] `brand` 非空
- [ ] `--platforms-json` 是嵌套对象、至少一个平台为 douyin/wx_video ← **硬门槛**
- [ ] 该平台至少含一个有效账号或关键词 ← **硬门槛**（账号→抓该账号视频；关键词→抓热门词相关视频）
- [ ] 账号总数 ≤200、关键词总数 ≤200
- [ ] `accounts_content_limit` / `keywords_content_limit` ∈ 1–20（未给走默认 5）

任一不达标 → 只补全、**不发请求、不扣点**。脚本侧兜底：硬门槛缺失退出码 3、不发网络请求
（提示"至少要给一个平台的有效账号或关键词"）；服务端若仍收到空源，嵌套形态返 `400 At least one
account or keyword is required`、扁平/缺字段返 `422`（detail 为空）。

### 门② · 报告生成前（调 resume 前）

满足全部才发请求：

- [ ] 已与用户对齐「分析什么/输出什么」并写成一段调研诉求（user_prompt）
- [ ] 该诉求非空

任一不达标 → 回用户对齐，不发 resume。脚本侧兜底：user_prompt 空则退出码 3 不发请求。

## 三阶段交互节奏

> ⚠️ **高成本 + 长耗时任务前置确认（必做）**：整套任务要"找视频→读视频原始内容→整理→分析→生成报告"，
> **整个过程通常半小时以上**，且 **1000 点起步、甚至更多**，视频越多越久、越耗点。**阶段1 create 前
> 必须同时告知"耗时长 + 耗点多"并让用户确认**，用户明确同意才开跑；嫌贵/嫌久则帮其减少关键词/每源条数
> 后重估再确认。详见 SKILL.md「扣点与确认」。

- **阶段1 采集**：`create_task.py`（deferred）建任务后内联轮询到 `awaiting_prompt`，采集耗时取决于账号/
  关键词数量与上限，通常数十秒到数分钟。采集期间告诉用户在采集、稍候；阶段(stage)变了简短转述；
  提示"视频越多越耗点"。
- **全程进度同步（避免像卡死）**：采集/生成期间，**每隔约 60–90s 用 `poll_task.py --once --task-id <id>`
  查一次当前 `STAGE`**，并把 stage 翻译成人话同步给用户（capturing→"正在抓视频+读原始内容"、
  analyzing→"正在分析+生成报告"）；同阶段停留也要定期说"还在 X 阶段、正常运行中"。阻塞脚本自身也在
  stderr 打心跳（同阶段超 30s）。详见 SKILL.md「进度同步」。
- **阶段2 采集后对齐**：`awaiting_prompt` 后与用户对齐分析方向，写成调研诉求文件
  `research-goal-<task_id>.md`（见 SKILL.md「采集后对齐」）。这是确认「诉求」而非「报告章节结构」，
  服务端会基于诉求+素材自己现造框架出报告。
- **阶段3 生成报告**：`resume_task.py` 推诉求后内联轮询到 `completed`，content 直返 Markdown。
  服务端一条龙（现造分析+生成报告），通常几十秒到几分钟。
- **异常先查再判**：遇非0退出码，先 `poll_task.py --once` 查真实 `stage`/`next_action`，按 SKILL.md
  「异常→继续决策」找继续路径（超时→续等、failed→retry 复用采集、awaiting_prompt→补诉求），别让用户白从头来。
- **成功交付（务必三件全做）**：① 确认 content 非空、**真正落地为 .md 文件并回读校验**（杜绝"没渲染成
  md"）；② 告知**本次实际扣点**（脚本 stdout 的 `POINTS_USED=`，为空则按规模估"约X点"，让用户去账户后台
  核对）；③ 告知**报告查看方式**（文件绝对路径 + 对话内已渲染）。详见 SKILL.md「输出交付」。
- **失败兜底（点数必告知返还）**：任务已发起但未出报告的失败（退出码 11/12、放弃等待的 13），统一告知
  "因网络原因本次任务执行失败，相应点数已返还"，问是否重试；任务没发起的（2/3/4/8）不涉及点数。
- **超时**：脚本默认 2400s 超时（退出码 13，非失败），告诉用户"还在跑，我再等一轮"，
  再跑一次对应脚本（poll/resume）续等；可用环境变量 `POLL_TIMEOUT_SECONDS` 调大。
- **交付后**：主动问是否需要就某章节深挖、或调整诉求重跑（复用同一 task 采集，重新 resume 新诉求即可出新报告，不重采）。

## 错误码面向用户的引导

四个脚本（create/poll/resume/retry）共用同一套退出码：

| 退出码 | 对用户说 |
|--------|----------|
| 2 缺 key | 引导去 auth 链接取 key、写入 config.json 的 LY_API_KEY |
| 3 参数非法 | 多为必填没补全或超限；若 422 多半是 platforms 用了扁平 schema 或误带 prompt_mode。讲清原因补完再采 |
| 4 余额不足 | 余额不够，充值后再来；任务没扣费 |
| 8 鉴权失败 | key 失效了，换个新 key |
| 10 其他 4xx | 透出服务端 message；404=任务找不着，409=状态不对（多半流程走岔了，先 poll 看现状） |
| 11 5xx/网络 | 因网络原因任务失败；告知"点数已返还"，稍后重试 |
| 12 任务失败 | 采集/生成失败；告知"因网络原因本次任务执行失败，相应点数已返还"，问要不要 retry |
| 13 轮询超时 | 还在跑，继续等；用户放弃则告知"未完成的已发起任务会返还点数" |

## 免责声明（交付报告时附一句）

- 报告基于采集素材与 AI 分析，为参考性结论，不承诺精确；重大运营/投放决策建议人工复核。
- 采集范围受平台公开数据与账号/关键词覆盖度限制，未覆盖内容不会出现。
- 分析框架由服务端基于你的调研诉求现造，可能未穷尽所有视角；如需补充方向可调整诉求重新 resume（复用采集，不重采）。
